**本轮仅进行分析与提案。不要生成业务实现代码、不要安装大型依赖、不要宣称架构已获批准，也不要把草案当成最终架构。** 即使当前仓库为空，也先完成问题澄清；不自行初始化完整应用。发现仓库已有内容时先检查，避免覆盖。

请按以下顺序输出，使用中文、Markdown 表格和可复核的具体条目：

1. **阻塞问题清单**：每项说明原因、影响、两种方案、推荐默认值及是否阻塞开发。至少覆盖操作系统/架构、MC 版本范围、Java 范围、加载器阶段拆分、微软 OAuth 外部凭据、联机选型、中继策略、后台边界、皮肤托管、邮件发送、凭证存储、自动更新签名，并处理 `docs/DECISIONS.md` 的原文歧义。明确标注 `待确认`。
2. **假设清单和完整支持矩阵**：矩阵列包含“能力 / 所属阶段 / 是否首版必须 / 依赖 / 验收标准 / 合规前提”，具体包括 OS/架构、MC、Java、加载器、账户、联网。对任何不确定覆盖范围都用“候选/待确认”，不得承诺已验证的全版本支持。
3. **客户端、后台、第三方服务边界**：分别列出责任、接口依赖、安全/数据流、生产运行前提；不得把后台实现塞进客户端。
4. **风险 spike 清单及验收标准**：至少包括 Forge/NeoForge 安装器、微软 OAuth loopback + PKCE、EasyTier/Terracotta + TUN/UAC、自动更新签名、清单信任源、SQLite 密文凭证。写明如何隔离在 `spikes/`，以及成功/失败判据。
5. **基于假设的目录与模块划分草案**：分层 core/services/ipc/ui/shared，阐明依赖方向、可测试边界和文档位置；仅是提案，禁止擅自将草案标记为批准。
6. **首批 core 纯逻辑模块**：版本解析、路径/隔离映射、哈希校验、下载调度状态机、启动参数拼装；写职责、输入输出、异常边界和测试样本。
7. **IPC 契约草案**：按 `domain:action` 命名；每项列请求 schema、响应 schema、错误码、超时/取消/订阅与退订、版本兼容策略、安全与 sender 校验。
8. **阶段 0 与阶段 1A 的可执行任务拆解**：按依赖顺序拆成小型可验证任务；每个任务写产物、前置审批、依赖、测试/手动验证方法。阶段 1A 只是规划，不立即实现。
9. **ADR 清单**：按重要性排序，写待决事项、选项、推荐、影响范围和批准负责人（用户），不虚构批准时间。
