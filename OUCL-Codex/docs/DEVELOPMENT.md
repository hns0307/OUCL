# OUCL 开发规范与交付流程

更新日期：2026-10-24。本文整理现有规则并提供阅读索引；持久约束以根级 [AGENTS.md](../../AGENTS.md) 为准。最新已批准默认设计方向、阶段0本地验证和空骨架；执行证据与缺项见TASK_PLAN，正式业务仍按指定增量启动。

## 1. 每次任务的读取顺序

1. **先读 [TASK_PLAN.md](TASK_PLAN.md)**，确认当前阶段、任务ID、执行状态与验收证据。
2. 读取根级 [AGENTS.md](../../AGENTS.md) 与 [DECISIONS.md](DECISIONS.md)，核对当前 G0/G1/G2、用户批准原文、日期和授权范围。
3. 阅读 [REQUIREMENTS.md](REQUIREMENTS.md) 的原始需求及当前任务相关设计；已经识别的阶段矛盾按 [DESIGN_REVIEW.md](DESIGN_REVIEW.md) 追溯，不能重复扩大首版范围。
4. 检查真实仓库状态、已有变更与实际脚本。先说明目标、拟改文件、依赖/风险和验证方式，再执行已授权增量。

TASK_PLAN 记录执行范围与证据，DECISIONS 记录授权；二者必须一致。任务已列出、推荐默认值、文档已交付或用户沉默都不等于批准。记录缺失或互相冲突时暂停受影响实现并澄清，不自行改写历史批准。

## 3. 门禁与阶段

| 门禁 | 可执行范围 | 进入下一步的条件 |
| --- | --- | --- |
| G0，当前状态 | 已授权文档；另行获准的限定spike或预先准备 | 架构、目录、IPC、存储、安全、联机六类基线明确批准；延期须有明确授权 |
| G1 | 批准范围内的目录、类型、空契约、构建与测试骨架 | 用户明确启动具体业务增量或明确解决 D-14 |
| G2 | 获批阶段内的一个可验证增量 | 验证、文档同步与验收后，再按有效授权安排下一增量 |

阶段0负责验证与基线；1A为原版离线首版；1B/1C为加载器，1D为修复，1E只是导入候选；2为社团能力，3为联机，4为认证与皮肤，5为增强。详细范围只在 TASK_PLAN 与提案维护，不因完成前一阶段而自动启动下一阶段。

架构、IPC、存储格式、合规边界、第三方依赖、联机选型发生变化须重新批准。外部条件缺失标记受影响任务 BLOCKED，注明解除条件；允许继续有效授权内的独立工作。

## 4. 编码、安全与依赖核对

以下是既有规范摘要，具体边界查阅 AGENTS §4–5 与提案，不是对候选架构的新增批准。

- 暂定 TypeScript strict、Electron、React、pnpm；禁止 `any`，必要时使用 `unknown` 与类型守卫。命名、JSDoc、统一错误分类与集中中文文案遵循 AGENTS。
- core 保持纯逻辑；真实IO由主进程 services/adapters 或有界 worker 承担；renderer 不直接访问 Node。main 显式装配并释放服务。
- IPC 先冻结共享类型、schema、错误、超时、取消、事件订阅/退订和版本语义；采用白名单与 sender/对象归属校验。
- Electron 隔离、sandbox、CSP 与 preload 限定接口；禁止任意路径、SQL、shell 或脚本透传。
- 可信上游摘要决定制品身份，镜像只传输；敏感凭证不落明文，日志默认脱敏；上报默认关闭。共享软链接不连接可写玩家数据，删除不得沿链接破坏共享目标。
- 新依赖先提交用途、固定版本、体积证据或测量方案、许可证、维护与安全情况、替代方案，经批准后安装；不能把参考设计授权解释为源码移植或依赖授权。

## 5. 验证与交付

| 改动类型 | 所需证据 |
| --- | --- |
| 纯文档 | 路径、仓库内链接、任务ID、状态与批准记录一致；不将静态检查记为运行验收 |
| core逻辑 | 独立单测覆盖正常、边界和错误；不依赖Electron或真实网络 |
| IPC / IO服务 | 契约校验、越权拒绝、取消/重试/恢复；临时目录、可控网络及进程替身 |
| 启动/下载/隔离等关键链路 | 集成/E2E或可复现实机步骤；按批准平台与版本分别留证 |
| 增量交付 | 运行仓库实际存在的适用类型检查、lint、单测、构建；记录失败或不可用原因 |

当前根级已建立package.json、pnpm锁文件和CI。适用命令：`pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build`（合并为`pnpm check`）、`pnpm test:spikes`、`pnpm audit --audit-level=high`、`pnpm audit:licenses`、`pnpm smoke`、`pnpm package:dir`、`pnpm smoke:package`。必须以实际执行证据报告，不把CI配置当成远端运行通过。core首次业务增量再建立已批默认85%行/分支目标，本轮不制造空core的覆盖率。

记录环境、文件快照或提交、输入、真实命令/步骤、预期与实际结果；使用 TASK_PLAN §6 模板。没有运行、只有mock或缺生产条件的能力不标生产通过。执行交付与用户验收分开，Codex 不替用户签署验收。

提交/PR 使用 Conventional Commits，并附变更范围及验证结果。提交时只包含当前授权文件，不将用户已有未跟踪内容一并纳入。交付报告列明完成项、文件、验证、未完成/阻塞、下一最小增量；完成报告后停止，不自动实施后续全部功能。
