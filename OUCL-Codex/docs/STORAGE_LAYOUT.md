## 1. 目录安排

### 身份定义（本轮修订）

- instanceId：OUCL稳定UUID，用于UI/IPC，不随显示名变化。
- directoryId：主进程分配的安全目录名，用户不能用显示名指定路径。
- mcVersionId：上游基础版本标识；多个实例可使用同一版本。
- `versionRecordId`：本游戏根内受管的版本记录ID；实例描述和隐藏依赖均有记录，不能把它与UI实例混为一谈。

上游version JSON按可信来源保存为原始输入，实例描述由解析结果和本地记录映射生成；不直接重命名上游id后假定inheritsFrom和jar仍有效。子描述的inheritsFrom必须指向根内已登记记录，jar回溯使用此图。删除可见父实例时，仍被子实例引用的版本描述与jar入口保留为隐藏依赖记录；只删除无引用的实例私有数据。依赖记录同样进入备份、恢复和GC标记集合。

图中“实例目录ID”即directoryId；元数据显式保存上述映射。隐藏依赖目录只有受管版本描述和必要制品，不包含玩家存档。

源码仓库与用户游戏数据分开。用户首次选择一个固定的OUCL数据目录，可放在容量充足的盘；不是把游戏缓存放进Git仓库。下图名称为逻辑约定，不硬编码盘符。

```text
<OUCL数据目录>/
  store/                              # 固定共享仓库
    objects/sha256/<前两位>/<完整摘要>   # 已验证文件本体，每份内容一份
    views/<rootId>/                    # 为游戏根提供兼容目录结构
      assets/                         # 路径视图，文件链接到objects
      libraries/                      # Maven路径视图，文件链接到objects
    runtimes/<发行商-版本-架构>/          # 每个精确Java运行时一套
    staging/                          # 下载.part、校验、隔离安装工作区
    trash/                            # 待回收对象，延迟删除
  roots/<rootId>/.minecraft/
    assets/             => store/views/<rootId>/assets/
    libraries/          => store/views/<rootId>/libraries/
    launcher_profiles.json            # 该游戏根内共享，不跨根共用可写配置
    versions/
      <实例目录ID>/
        <实例目录ID>.json              # 实例自己的版本描述
        <实例目录ID>.jar => store/objects/...  # 有自身client jar才建立
        oucl.instance.json            # 实例元数据及文件引用清单
        mods/
          example.jar   => store/objects/...
        resourcepacks/
          example.zip   => store/objects/...
        shaderpacks/
          example.zip   => store/objects/...
        config/                       # 实例私有
        saves/                        # 实例私有
        logs/                         # 实例私有
        crash-reports/                # 实例私有
        screenshots/                  # 实例私有
        natives/                      # 实例私有，每次启动前重建
        options.txt                   # 实例私有
        servers.dat                   # 实例私有
```

`=>`表示受管链接，不表示复制。存档、截图等目录按实际使用创建，不预先制造空文件。账户、设置、SQLite索引仍使用提案规定的应用数据目录；索引保存storeId和相对对象ID，运行时解析固定仓库的实际路径。

保持原需求路径语义：assets/libraries始终从`.minecraft`根访问，不能出现在各实例下；classpath使用根/libraries绝对路径，assetsDir使用根/assets。继承实例没有自身jar时仍沿继承链找到最近祖先jar，不给每个子实例创建父jar副本或额外伪装的子jar。全局Java可直接按登记路径使用，不为每实例复制或制造无用链接。

不同root的assets/libraries路径视图可以不同，底层相同内容仍指向同一个对象，避免同一库坐标对应不同字节时互相覆盖。一个root内发生相同逻辑路径、不同摘要冲突时拒绝静默覆盖，要求隔离到另一兼容视图/游戏根并报告原因。

## 2. 文件复用范围

### 隔离语义与兼容例外（本轮修订）

下表的“实例私有”仅适用于隔离模式。非隔离模式明确共用本游戏根的gameDir，因此mods/config/saves/logs/options等都属于该根共享玩家数据；不承诺两个非隔离实例互不影响。整合包必须隔离，全局默认开启隔离。

会话对解析后的gameDir及实例持排他锁：同一非隔离根一次只允许一个游戏会话，写入该根玩家数据的安装/迁移也不能与运行并发。复制非隔离实例默认只复制版本定义和设置，不复制根玩家数据；删除只移除实例入口及引用，不递归删除根mods/config/saves。切换隔离只修改下一次启动的目录策略，预览明确“原存档留在原位置”；迁移玩家数据必须另行计划。启动器只能约束自己受管的进程与文件操作，不能承诺约束手工启动的外部游戏进程。

| 文件类别 | 保存/复用方式 | 写入与隔离规则 |
| --- | --- | --- |
| 官方client JAR、库JAR、assets对象、可信资源索引 | 内容对象只存一次，兼容路径建立受管文件软链接 | 源制品按不可变内容处理；新版本写新对象，不原地覆盖旧对象 |
| 同一精确版本Java运行时 | 全局runtimes一套，多实例登记引用 | 不共享“Java 21”这类会漂移的路径；固定发行商、完整版本、架构和制品摘要 |
| Mod JAR、只读资源包/光影ZIP | 每个实例保留独立目录，内容相同的文件逐个链接到对象仓库 | 仅在允许链接的兼容策略下复用；禁用Mod只改本实例链接名；更新只替换本实例链接 |
| 会被修补、自修改或依赖真实路径的Mod/资源 | 从已验证对象创建实例私有副本 | 缓存下载制品仍可去重；运行副本有必要的独立磁盘开销，不能承诺全部文件零复制 |
| Forge/NeoForge安装器输入与生成制品 | 安装输入可复用；安装器先在独立staging处理，成功后冻结可复用输出 | 不允许安装器通过链接直接改共享仓库；生成内容的来源与安装配方另记 |
| config/defaultconfigs、存档、日志、截图、options、servers及解压的包目录 | 实例私有真实文件/目录 | 初始模板可以缓存，但第一次使用时复制为私有；不链接可写玩家数据 |
| natives | 下载的原生库归档可复用，解压结果实例私有 | 在实例锁保护下重建；不能把整个natives链接到公共可清空目录 |
| 旧版虚拟assets/resources适配目录 | 依据旧版spike确定 | 只读对象可复用；需复制/修改的兼容内容建立私有视图，不擅自认为现代布局适用于所有旧版 |

**不把整个mods/resourcepacks/shaderpacks目录链接到一个公共目录。** 两个实例可以拥有不同文件列表、文件名和Mod版本，仅相同内容的文件共享本体。文件名相同但哈希不同保存为两个对象，文件名不同但内容相同可指向同一对象。

软链接不是写时复制：经任一链接原地写入，都会改动共享目标。OUCL自身编辑/修补前必须“解除本实例链接 → 从已验证对象生成私有临时副本 → 完成修改 → 原子替换本实例入口”；更新则写新摘要对象，再替换该实例链接。两种路径都不原地覆盖共享对象。

共享对象采用只读策略及完整性检查，无法把它描述成隔离同用户外部程序的安全沙箱。不能拦截玩家用外部编辑器修改或某个Mod任意写文件；已知有此行为的内容使用私有副本。正式采用链接前必须验证各加载器、扫描器及Mod兼容性；运行前发现损坏就使对象失效、重新校验下载并恢复引用，不能据此保证已运行中的其他实例不受外部篡改影响。

## 3. 防止重复下载

1. 从可信元数据获得预期摘要/算法/大小；镜像只提供传输地址。同名文件、相同URL都不足以证明内容相同。
2. 查询对象索引和实例引用。已有匹配对象且完成必要完整性验证时，直接建立链接，不重新下载。同一官方SHA1等外部摘要可以映射到本地SHA256对象；本地摘要不替代官方信任链。
3. 同时安装多个实例时，按可信制品身份建立共享下载任务：同一文件只有一个实际传输任务，其他请求等待同一结果。不同来源只凭本地算出的哈希相等，可以节省存储，不能因此升级来源信任等级。
4. `.part`文件、已接收区间和ETag/Last-Modified等恢复信息统一归共享任务。续传校验响应与制品身份，源变化时重置或验证；多个任务不各自下载一份。任务跨窗口/重启恢复依赖SQLite事务及单写进程/仓库锁。
5. 下载完成后同时核对可信预期摘要/大小并计算SHA256；合格才从同卷staging原子提交到objects。并发提交遇到同一对象时验证既有对象再合并，不覆盖不明内容。
6. 为每个实例生成独立的引用清单并创建链接；元数据提交和文件操作使用可恢复事务。用户中断时，只保留可恢复的部分文件或清理staging，不登记半成品ready。

“共享下载任务”与实例安装任务分开。实例A取消等待，只解除A的需求；只要B仍需该制品就继续传输。最后一个消费者离开时才暂停/取消底层传输，避免取消一个实例影响所有人。实例进度可以引用同一传输进度，但网络流量统计只计一次。

### 3.1 权威记录与可恢复提交（本轮修订）

- 实例JSON记录已提交revision及文件引用；根内隐藏依赖清单记录版本图；对象旁的版本化来源记录保存可信预期摘要、来源身份和校验结果。凭本地SHA256不能恢复来源信任，来源证据缺失时重新从可信元数据验证。
- SQLite中的对象搜索索引是可重建缓存；操作日志、幂等受理记录和任务恢复状态不是可任意丢弃的索引。数据库损坏时先恢复日志/备份，未能证明状态完整则停写、停GC并展示待恢复；不得直接建空库后继续删除。
- 每个变更使用operationId、目标instanceId、expectedRevision、旧/新清单摘要和暂存/备份位置。先持久化PREPARED日志并固定对象租约，再准备已校验对象与新清单；在实例锁内记录APPLYING，逐项替换受管入口并保留撤销信息。
- 所有新入口验证后，原子替换实例JSON到新revision作为提交点，再登记COMMITTED、释放临时租约并延后清理旧内容。SQLite和文件系统不是一个原子事务；启动恢复必须先于IPC写操作和GC开放。
- 崩溃恢复：JSON仍是旧revision则依据撤销记录恢复旧入口；JSON已是新revision则核实新入口并补齐COMMITTED。任何不匹配/来源不明情况进入needsRecovery，禁止启动、迁移和回收，不能猜测成功。记录缺失时保守保留现场。
- 玩家存档不进入制品替换事务；跨卷操作采用目标卷staging、复制校验及可恢复切换，不能用一次rename承诺跨卷原子性。

上述格式随ADR-005冻结，S-07/S-10覆盖每个持久化边界的中断恢复。

## 4. Windows链接适配

优先满足用户提出的软链接方向，具体能力在选定磁盘上探测后决定，不要求整个启动器以管理员身份运行。

| 对象 | 首选 | 不满足条件时 |
| --- | --- | --- |
| assets/libraries目录入口 | 本地目录junction（目录联接） | 若文件系统/目标不可用则报告，使用普通目录路径视图；不链接网络共享 |
| JAR/ZIP等文件入口 | 文件symbolic link（软链接） | 不自动提权/开启开发者模式；显示能力限制，允许兼容复制模式 |
| 同卷不可变文件优化候选 | 经验证后可选hard link（硬链接），并在清单记录真实类型 | 硬链接不是软链接，只适用于同卷文件，也没有写时复制；跨卷不使用 |

Windows创建文件软链接受系统策略、权限和开发者模式等条件影响，实际必须探测；开发者模式允许的无提权创建需要适当API标志。junction可以指向另一块本地盘的目录，文件硬链接局限于同一卷。这些差异见微软的[软链接创建说明](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinkw)和[硬链接与junction说明](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)。不将复制回退伪装成已节省磁盘；界面分别显示逻辑大小、实际共享大小和私有副本开销。

目录联接并不能解决单文件软链接权限问题：若游戏必须看到实体文件且又不能建文件链接，只能使用获准硬链接策略或私有副本，不能声称junction可以任意替代单文件链接。

## 5. 删除、回收、迁移与链接安全

- 删除实例时先锁定/停止相关运行与安装任务；删除该实例的入口、私有文件及引用，不跟随受管链接递归删除共享目标。共享内容的保留量与私有数据删除范围在预览中分开显示。
- 回收不能只信可能失真的引用计数。先扫描有效实例清单、隐藏版本依赖、运行会话/下载任务/未完成操作租约以及备份/回滚保留项；不明记录或待恢复事务存在时保守保留。确认无引用的对象进入trash宽限期，再次检查后才删除。索引丢失时可重建，不能把“索引无记录”当成“对象没人用”。
- 根路径视图是派生投影，不把所有历史投影永久当作引用根。先标记上述权威引用，再移除无人需要的受管投影，最后将无引用对象移入trash；未知外部使用或无法解释的入口保守保留并报告。root内同一逻辑路径不同摘要仍拒绝静默覆盖。
- 新建引用、回收和对象提交使用一致的锁/租约顺序，防止刚建立链接就被GC删除。引用声明与事务恢复必须在移动垃圾对象前复核。
- 应用主动创建的链接登记在受管清单，目的地必须是已登记store中的相符摘要对象/视图；导入压缩包自带的软链接、junction和其他reparse point仍拒绝。不能因为支持受管链接就允许外部任意链接。
- 普通私有目录出现未知链接时中止受影响的写入/删除；路径操作需逐级验证reparse point与目标，不能只做字符串前缀比较，也不能先检查后无保护地跟随可能被替换的链接。
- 迁移固定共享仓库须作为单独维护操作：停止受影响任务/会话、迁移并校验对象、按清单重建绝对链接、确认所有根可用后切换store位置，保留旧位置供失败恢复。不把“移动文件夹”当成链接自动跟随保证。
- 导出自包含整合包/备份时按授权展开链接内容，重新校验并限制范围，不导出指向本机仓库的裸链接。仅用于同机恢复的引用式备份须明确依赖仓库，并计入回收保留项。

| 场景 | 预期结果 |
| --- | --- |
| 两实例同时安装同一份Mod/库 | 实际传输一次、对象本体一份，两份实例入口；取消一个仍能完成另一个 |

| 删除实例/清空natives/回收缓存 | 不穿过链接删除对象；仍有运行/备份/安装引用的文件不被回收 |
| 无软链接权限、跨盘、非支持文件系统、断链/目标损坏 | 明确反馈并按兼容策略降级或修复；不默默请求管理员权限 |
| 进程中断、磁盘满、GC与安装并发、索引丢失 | 清单可恢复，半成品不ready；有效对象不误删；无重复提交污染 |
| 导入含恶意链接/导出/迁移 | 导入拒绝越界；导出内容完整且不携带本机裸链接；迁移可恢复 |

实现拆分建议：先做core对象身份/路径与引用计划，再做store与事务、共享下载协调、受管链接适配、实例物化/更新、回收与迁移。每项先定义适用IPC/存储schema及测试，放入后续获准增量；本轮只更新文档，没有对现有玩家文件建立任何链接或移动数据。

## 7. 首版裁剪

1A交付对象复用、共享下载、受管软链接/目录视图、明确的复制回退、引用和崩溃恢复。硬链接仅为后续候选，不进入首版自动回退链。自动GC、跨卷仓库迁移界面、资源包编辑及引用式备份界面后续独立增量交付；首版安全保留未引用对象并显示空间占用，不能以未实现GC冒充自动释放空间。删除实例仍必须保留所有有效共享引用。S-10先用假文件验证GC计划与误删边界，不要求首版发布自动清理功能。
